Summary: Enter your home's measurements and get a complete DuraVent DuraTech chimney parts list that follows the manufacturer's installation rules and NFPA 211.

Planning a wood-stove or fireplace chimney means cross-referencing a thick manufacturer catalog, clearance rules, and NFPA 211. This planner does it for you: describe the installation and it returns every part you need, with quantities and part numbers.

What it does

- Walks you through the appliance, ceiling, attic, and roof measurements, or loads a worked example to start from.

- Applies the strictest rule among the DuraVent guideline, NFPA 211, and your appliance manual’s own limits.

- Works for any stove or fireplace: you enter what its manual requires, so the planner never falls behind new models.

Built for

Coming next

A planning aid, not an installation approval. Follow local code and have the finished system inspected by a certified professional.

=== Vendor Price Sheet → Jobber Import ETL ===
Status: Active / current (Live · in development), 2019–2026
Project page: https://www.davidcreason.com/projects/jobber-import-etl/
Links: Launch the demo: https://project-creason.github.io/jobber_import_etl/; Source on GitHub: https://github.com/project-creason/jobber_import_etl
Tags: Python, pandas, ETL, Data quality, Jobber
Summary: A config-driven Python pipeline that turns any manufacturer's price sheet into a clean, validated Jobber product import, with every rejected row explained.

Crestwood Home & Hearth sold and installed products from many manufacturers, and Jobber, its field-service software, needed every one of them in its product list. Each manufacturer publishes its price sheet in its own layout, so each Jobber import file was built one vendor at a time. This pipeline replaces that with one repeatable run.

The problem

- No two price sheets match. One manufacturer's sheet has part number, list, net, UPC, weight, and box dimensions; another has a model number and a single price.

- Jobber accepts exactly five columns: name, description, price, taxable, and category.

- The sheets carry small data problems that break an import or show up on a customer's quote: broken characters, inch marks, prices stored as text, placeholder rows, and duplicates.

The approach

- Extract: reads Excel or CSV, finds the header row under any title banner, detects the text encoding, and picks the right sheet.

- Transform: maps each vendor's columns to Jobber's five, adds the vendor prefix to the SKU, parses prices, and cleans the text.

- Validate: rows with no SKU, no price, or a $0 price, and duplicate SKUs, go to a rejects file with the reason.

- Load: writes the Jobber CSV, the rejects file, and a run report.

What the cleanup actually fixes

Every example below is a real row from a manufacturer's catalog.

| | Problem | In the price sheet | In the Jobber import

| Prices stored as text | List: "6,022.00" | Cost: 6022
| SKU needs a vendor prefix | 017-01-H-SM-RBC | AFD 017-01-H-SM-RBC
| Two apostrophes used as an inch mark | 9.69’’ (246MM) CEILING MOUNT POLE | 9.69" (246MM) CEILING MOUNT POLE
| Hidden control character from a Windows export | 8"␝ x 5.5"␝ | 8" x 5.5"
| Escaped symbols | COVER,AFD \#435 BRDX LARGE | COVER,AFD #435 BRDX LARGE
| $0 placeholder row | STAND - TUNGSTEN PORTABLE - BOX 2 OF 2, 0 | Rejected: zero price

Design choices

- Configuration, not code. Each vendor is a short entry in a JSON file: which file names it matches, its SKU prefix, and which columns hold the SKU, description, and price. Adding a manufacturer takes a minute.

- Nothing disappears silently. Every dropped row lands in a rejects file with the reason, so a person can fix the source instead of guessing.

- Safe to re-run. Finished Jobber files are skipped, and SKUs that already carry a prefix don't get a second one.

- Pricing is a setting. Use the list price as is, or start from dealer cost with a markup.

Results so far

- Tested on real rows from three manufacturers, chosen because they contain the problems above.

- 15 rows imported cleanly; 3 rejected, each with the correct reason: a missing price, a $0 item, and a duplicate part number.

Try it, and what's next

- Try the live demo : run the sample price sheets or your own, right in the browser. It runs the same Python code as the repo, and files never leave your computer.

- Run it on every full price sheet in the catalog.

- Watch a shared Drive folder and convert new price sheets automatically when they arrive.

=== Property ETL Bench ===
Status: Active / current (In use · built for a REIT), 2026
Project page: https://www.davidcreason.com/projects/property-etl-bench/
Links: Read the case study: https://www.davidcreason.com/projects/property-etl-bench/
Tags: JavaScript, HTML, CSS, ETL, Yardi Voyager, Batch processing, AI-assisted development
Summary: A browser-based ETL tool that turns raw property spreadsheets into Yardi Voyager import files, setting up about 30 properties in a few minutes instead of 5+ hours by hand.

Every time a property joined the portfolio, its details arrived as a spreadsheet that someone reshaped by hand into the import files Yardi Voyager expects. I built a browser tool that does the whole batch in one pass.

The problem

- New property details arrived as spreadsheets, but Yardi Voyager only accepts its own import layouts.

- Each property took 10 to 15 minutes of repetitive, careful reshaping by hand.

- A mistyped code or a missed column usually didn't surface until the import failed, or until bad data was already in the system.

The approach

- Parse & normalize: reads the spreadsheet, standardizes headers, and trims and types every value.

- Validate & map: checks required fields and formats, then maps source columns to the target import layout. Problems are flagged inline before anything is generated.

- Generate: writes the Yardi import CSVs for every property in the batch at once.

- Review & export: the user previews every output before downloading, so a person stays in the loop.

Results

- 10–15 min per property, done by hand before

- ~30 properties set up in the most recent run

- Minutes for the entire batch, versus 5+ hours by hand

Catching bad data at the validation step also means import errors get fixed in seconds by the person who has the context, instead of being discovered later in Yardi.

Built to extend

- Parsing and validation are separate from output generation, so supporting another target system means adding a new mapping and output step. The front half stays the same.

- The pattern fits any organization that loads records from spreadsheets into one or more systems of record, well beyond real estate.

- Plain JavaScript, HTML, and CSS in a single page: no server to stand up or secure, and the data never leaves the user's computer.

What I'd highlight

- Business analysis first. The hard part was understanding the target system's import rules well enough to encode them, not writing the transformation.

- AI-assisted development. I built it with an AI coding assistant, moving quickly from requirements to working software while I owned the design, the data rules, and the testing.

- Designed for the operator. Inline validation and a review step make it safe for someone who isn't an engineer to run.

This tool was built for an employer, so the source code and real data aren't published here. The diagram and descriptions are simplified and contain no proprietary mappings or business rules.

For the two-course IT Systems Project capstone in my M.S. in Applied Information Technology, our team analyzed the operations of a local meal-delivery company and built a customer management system around how it actually worked.

=== ITIL Service Management Assessments ===
Status: Past (Graduate coursework), 2011
Project page: https://www.davidcreason.com/projects/itil-service-management/
Links: Read more: https://www.davidcreason.com/projects/itil-service-management/
Tags: ITIL service lifecycle, Service level management, IT service continuity, Supplier management
Summary: For my M.S. ITIL course, I assessed two fictional companies, a global resort operator and a mobile music service, and wrote recommendations to IT leadership on service portfolios, SLAs, supplier contracts, continuity, and change management.

In my M.S. course on IT Planning & Service Management Using ITIL, each assignment put me inside a fictional company with real-world IT problems and asked for recommendations to leadership. The companies were invented for the course; the analysis and recommendations below are mine.

Resort operator: an ITIL roadmap for the VP of IT

A global resort company with no defined list of IT services, weak service levels, and aging systems nobody had retired.

Service portfolio

- Defined the portfolio: a pipeline, a catalog of 12 live services (from the service desk to reservations, lodging, ski, golf, and club management), and a retired list.

- Showed how never retiring services had left legacy systems in place.

Service levels & suppliers

- Replaced unmeasurable SLAs with the full set: service level requirements, measurable SLAs, internal OLAs, and a service improvement plan.

- Specified OLAs with every department, Finance, and HR.

- Identified six outside suppliers that needed underpinning contracts, including 24/7 support for the business-critical website.

Continuity

- Assigned every service a recovery tier based on what an outage would cost the business (below).

| | Tier | Services | Why

| Immediate recovery | Reservations, Website, Lodging, Customer relationship management, Club management | Revenue stops the moment these go down. Reservations and the website serve guests across time zones around the clock, and club members are the most loyal customers.
| Fast recovery | Financial management, Material management | Used by nearly every division, but guests can still check in and stay while they're down. Purchasing still matters: guests notice when the restaurant runs out of something.
| Gradual recovery | Human resources | Not critical to daily operations, with paper records as a fallback. Restoring from backup is acceptable, and faster options would cost more than the downtime.
| Manual workaround | Ski management, Golf management | Each resort can take bookings by phone and in a daily planner until the system returns, the way it worked before computers.

Mobile music service: fix the foundation before expanding

A fast-growing company weighing two new lines of business, a mobile game and a dating app, after a 48-hour outage.

Recommendation

- Advised leadership to hold off on both launches until core IT service management was in place.

- In an earlier memo to leadership, explained what ITSM is and why it would align IT with the business: utility and warranty, clear ownership, and accountability.

Top three risks

- Availability: no formal service levels, and an implied 99.999% target already missed.

- People and legacy tech: a COBOL finance and procurement system, a shrinking talent pool, and falling morale.

- Change management: each office configured differently, no release management, and no known-error database.

Why it still matters

- It's the same judgment I use today: tie IT decisions to business impact, standardize before you scale, and put controls around change.
